# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 **십자가(Cross)** 와 **X** 패턴을 판별하는 Python 콘솔 애플리케이션입니다.
외부 라이브러리(NumPy 등) 없이 표준 라이브러리(`json`, `os`, `re`, `sys`, `time`)만 사용합니다.

## 실행 방법

```bash
python main.py
```

- Python 3.8 이상
- `data.json` 은 `main.py` 와 같은 폴더에 둡니다 (없으면 현재 작업 폴더를 확인).
- 실행하면 모드를 선택합니다.
  - `1` : 사용자 입력(3×3). 필터 A, 필터 B, 패턴을 3줄씩(공백 구분) 입력
  - `2` : `data.json` 분석. 5×5 / 13×13 / 25×25 케이스 일괄 판정 + 성능 분석 + 결과 요약

입력 예시 (모드 1)

```
필터 A        필터 B        패턴
0 1 0         1 0 1         1 0 1
1 1 1         0 1 0         0 1 0
0 1 0         1 0 1         1 0 1
→ A 점수 1.0 / B 점수 5.0 / 판정: B
```

## 구현 요약

| 항목 | 내용 |
|---|---|
| 데이터 구조 | `Matrix` 클래스 (n×n 2차원 리스트, `get`/`set`/`from_rows`/`flatten`) |
| MAC 연산 | `mac(pattern, filter)` — 이중 for문으로 위치별 곱 후 누적합 (점수는 float) |
| 라벨 정규화 | expected: `+`→`Cross`, `x`→`X` / 필터 키: `cross`→`Cross`, `x`→`X` (공백·대소문자 무시). 이후 모든 비교/출력은 표준 라벨 기준 |
| 동점 정책 | `abs(score_cross - score_x) < 1e-9` 이면 `UNDECIDED`. `UNDECIDED` 는 expected 와 다르므로 FAIL |
| 입력 검증 (모드 1) | 줄당 숫자 개수 불일치 / 숫자 파싱 실패 시 안내 문구 출력 후 해당 행렬을 처음부터 재입력 |
| 스키마 검증 (모드 2) | 패턴 키(`size_N_idx`) 파싱, 필터 존재/정사각/크기 일치, expected 라벨 유효성을 케이스 단위로 검사. 문제가 있으면 해당 케이스만 FAIL + 사유 기록 (프로그램은 계속 진행) |
| 성능 측정 | `time.perf_counter()` 로 MAC 함수 호출 구간만 측정, 크기별 10회 평균 (I/O 제외) |
| 보너스 | ① 2D → 1D(길이 N²) 변환 MAC 비교 ② `make_cross(n)` / `make_x(n)` 패턴 생성기 (성능 분석에 재사용) |

## 결과 리포트

### 실행 결과 (data.json)

총 테스트 6개 / 통과 3개 / 실패 3개

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

### 실패 원인 분석

1. 실패 3건(size_5_1, size_13_2, size_25_1)은 모두 **두 필터의 점수가 사실상 같아서 동점(UNDECIDED)** 이 된 경우입니다. 라벨/스키마 문제나 크기 불일치는 없었습니다.
2. **라벨/스키마 문제는 아닙니다.** expected 의 `+` / `x` 와 필터 키 `cross` / `x` 는 정규화 후 `Cross` / `X` 로 통일되어, 6건 모두 비교 대상이 정상적으로 매칭되었습니다. 정규화가 없었다면 `+` 와 `cross` 가 서로 달라 6건 모두 오탐 FAIL이 났을 것입니다.
3. **원인은 필터 가중치 설계(데이터 특성)입니다.** 필터 중앙값이 강조되어 있어 (size_5: 0.9, size_13 X 필터: 7.5, size_25 Cross 필터: 4.9) 서로 다른 모양의 입력이라도 점수가 같아지도록 값이 맞춰져 있습니다. 예: size_5_1(X 패턴)은 Cross 필터와 중앙 한 칸만 겹쳐 0.9점이고, X 필터는 0.1이 놓인 9칸과 모두 겹쳐 0.1×9 = 0.9점입니다.
4. size_25_1 도 같은 구조입니다. Cross 필터와는 중앙 1칸(4.9), X 필터와는 49칸 × 0.1 = 4.9. size_13_2 는 Cross 패턴이 Cross 필터 25칸 × 0.3 = 7.5, X 필터 중앙 7.5 와 같습니다.
5. **수치 비교 문제도 함께 드러납니다.** 이론상 같은 값인데 실제 계산은 `0.8999999999999999`, `7.499999999999997`, `4.899999999999999` 처럼 약 1e-15 오차가 생깁니다. 0.1, 0.3 은 이진 부동소수점으로 정확히 표현되지 않고, 더하는 순서에 따라 오차가 누적되기 때문입니다.
6. 만약 `==` 나 `>` 로 직접 비교했다면 오차 때문에 **우연히 한쪽이 이기는 결과**가 나왔을 것입니다 (예: size_5_1 은 Cross 가 0.9 로 더 커서 `Cross` 로 오판정). 그래서 `abs(a-b) < 1e-9` 허용오차(epsilon) 비교가 필요하며, 이 정책이 오차(≈1e-15)를 동점으로 안정적으로 묶어 줍니다.
7. 즉 로직 오류가 아니라 **"동점이면 UNDECIDED, UNDECIDED 는 FAIL"** 이라는 과제의 판정 규칙이 정상 동작한 결과입니다. 진단 분류는 데이터/스키마 문제 0건, 로직 문제 0건, 수치 비교(동점) 문제 3건입니다.
8. 개선 방향: 필터 가중치 합으로 점수를 정규화하거나(점수 ÷ 필터 가중치 합), 필터 설계를 바꿔 동점이 생기지 않게 하는 방법이 있습니다. 또는 동점일 때 보조 기준(겹친 칸 수 등)을 두는 방법도 있습니다. 다만 현재 과제 규칙은 동점을 UNDECIDED 로 두는 것이므로 그대로 구현했습니다.
9. 참고로 가중치가 균일한 0/1 필터(모드 1 의 예시 입력)에서는 점수가 정수이고 오차도 없어 A/B 가 명확히 갈립니다 (예시 입력: 1.0 vs 5.0).

### 성능 분석과 시간 복잡도 O(N²)

실측 (Cross 패턴 × X 필터, 각 10회 평균, 환경에 따라 값은 달라질 수 있음)

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | ns/연산 |
|---|---|---|---|
| 3×3 | 0.0008 | 9 | 약 89 |
| 5×5 | 0.0013 | 25 | 약 52 |
| 13×13 | 0.0059 | 169 | 약 35 |
| 25×25 | 0.0203 | 625 | 약 33 |

1. MAC 은 N×N 칸을 한 번씩 방문하며 곱셈 1회 + 덧셈 1회를 하므로 연산 횟수는 정확히 **N²** 입니다. 변수가 N 하나인 이중 루프이므로 시간 복잡도는 **O(N²)** 입니다.
2. 13×13 → 25×25 구간에서 연산 횟수는 169 → 625 로 약 3.70배, 측정 시간은 0.0059 → 0.0203 ms 로 약 3.44배 늘어 **연산 횟수에 거의 비례**합니다. 이 구간의 연산당 시간도 35 → 33 ns 로 일정합니다.
3. 3×3 → 25×25 로는 연산 횟수가 약 69배인데 시간은 약 25배만 늘었습니다. 크기가 작을 때는 함수 호출, 타이머 호출, 루프 설정 같은 **고정 비용**이 전체 시간의 큰 부분을 차지해 연산당 시간이 커 보이기 때문입니다. 크기가 커질수록 고정 비용이 희석되어 이론(N²)에 가까워집니다.
4. 이 오차는 측정 방식의 한계이기도 합니다. 10회 평균은 ms 이하 구간에서 OS 스케줄링 등 잡음에 민감하므로, 정밀한 비교에는 반복 횟수를 늘려야 합니다.
5. **보너스(1D 최적화)**: 2차원 리스트를 길이 N² 의 1차원 리스트로 펴서 단일 루프로 계산하면 작은 크기(3×3, 5×5)에서 약 25% 빨라졌습니다. 반면 25×25 에서는 효과가 없거나 오히려 약간 느려졌습니다. 1D 는 행 리스트 참조와 이중 루프 오버헤드를 줄이지만 `range(len)` 인덱싱 비용이 남아 있어 큰 크기에서는 이점이 사라집니다. 어느 쪽이든 **연산 횟수 N² 는 변하지 않으므로 복잡도는 여전히 O(N²)** 입니다.
6. 이것이 NPU 가 필요한 이유입니다. 25×25 한 장은 625 MAC 이지만, 고해상도 이미지와 수천 개의 필터가 만나면 수억 번의 MAC 가 되고, CPU 는 이를 순차 처리합니다. MAC 이 서로 독립적이어서 한꺼번에 처리하는 병렬 하드웨어가 유리합니다.
